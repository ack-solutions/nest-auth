Sessions are persisted server-side. You pick the backend on `session.storageType`.

## The three built-in stores

| Store | `SessionStorageType` | Best for |
|---|---|---|
| **Database** | `DATABASE` (default) | Single-instance apps, small/medium scale, transactional consistency with the rest of your data |
| **Redis** | `REDIS` | Multi-instance apps, horizontal scale, sub-ms read latency |
| **Memory** | `MEMORY` | Local development, tests, single-instance prototypes |

```ts
import { NestAuthModule, SessionStorageType } from '@ackplus/nest-auth';

NestAuthModule.forRoot({
  appName: 'my-app',
  session: {
    storageType: SessionStorageType.REDIS,
    redis: {
      host: process.env.REDIS_HOST,
      port: 6379,
      keyPrefix: 'auth:',
      // Standard ioredis options pass through.
    },
  },
});
```

## Database

The default. Sessions live in the `nest_auth_sessions` table. Every refresh, revoke, and lookup is one SQL query.

**Pros:** zero extra infrastructure, joins with the rest of your data, transactional with user updates, easy to inspect during debugging.

**Cons:** writes scale with login/refresh traffic. On high-traffic tenants with `slidingExpiration: true`, the table can become a write hot-spot — switch to Redis.

## Redis

Sessions live as Redis keys under your configured prefix. Refresh tokens are looked up by key — sub-millisecond on a warm cluster.

Set up:

```ts
session: {
  storageType: SessionStorageType.REDIS,
  redis: {
    host: 'redis.internal',
    port: 6379,
    db: 0,
    keyPrefix: 'auth:',
    password: process.env.REDIS_PASSWORD,
    // ioredis options:
    // - sentinels / cluster / TLS, retryStrategy, offlineQueue, …
  },
}
```

### Reusing your own Redis connection

Pass an existing ioredis client as `redis.client` and the library uses it instead of opening a second connection. One pool, one place to configure TLS, password, sentinel or cluster:

```ts
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);   // your app's connection

NestAuthModule.forRoot({
  session: {
    storageType: SessionStorageType.REDIS,
    redis: { client: redis, keyPrefix: 'auth:' },
  },
});
```

When `client` is set, the other connection fields (`url`, `host`, `port`, `password`, `tls`, …) are ignored; `keyPrefix` and `ttlSeconds` still apply. **Lifecycle stays with your app** — the library never calls `quit()` on a client it did not create, so shutting down Nest will not close a connection the rest of your app is still using.

### What happens if Redis goes down

The guard **fails closed**. A store outage is infrastructure failure, not a failed sign-in, so it is never read as "no session":

| | Response |
| --- | --- |
| Route with required auth | `503` · `SESSION_STORE_UNAVAILABLE` |
| Route with **optional** auth, caller presents a token | `503` · `SESSION_STORE_UNAVAILABLE` |
| Route with optional auth, no token at all | normal anonymous response |

`503` rather than `401` is deliberate. A `401` tells clients to sign the user out, so a brief Redis blip would log out your entire user base. `503` says *retry*. Handle it in your client as a transient error, not an auth failure.

The outage is logged **once** when it starts and once when it recovers, not once per request.

> **Security note.** Before 2.16.0 an optional-auth route silently fell back to **anonymous** during a Redis outage — the request was served with no user attached. Any such route that also carries `@NestAuthRoles` or `@NestAuthPermissions` was effectively open for the duration of the outage. Upgrading closes that.

**Pros:** horizontal scale, fast, automatic key expiry, no DB write pressure.

**Cons:** another service to operate. If Redis goes down, authenticated requests are refused with `503` until it returns — plan for failover.

See [Scaling](/docs/production/scaling) for the full `RedisSessionOptions` reference and recommended settings (sentinel / cluster / retry strategy / offline queue).

## Memory

Sessions live in a `Map` inside the Node process. Lost on restart. Lost when you scale to a second instance.

Use it for tests and local dev. **Never in production**, even single-instance — a deploy or crash logs every user out.

## Custom store

Implement a class that satisfies the session-store contract and pass it via the module config. The interface is small (create / find / refresh / revoke / list). See [`SessionManagerService`](/docs/backend/services).

## When sessions get cleaned up

| Trigger | What happens |
|---|---|
| User logs out | Their session row/key is deleted |
| User logs out of all devices | All their session rows/keys are deleted |
| Refresh token expires | Next refresh attempt errors; client logs out |
| `maxSessionsPerUser` exceeded | Oldest session evicted on next login |
| Password reset / change | All sessions for the user are revoked |

For DB-backed sessions on long retention, run a periodic cleanup of expired rows — Redis handles this automatically via key TTL.

## Custom store

The three built-ins (database, Redis, memory) cover most needs. For anything else — DynamoDB, Cloudflare KV, Mongo, a bespoke Redis-cluster wrapper — implement the `SessionStore` interface (or extend `BaseSessionRepository` for the shared expiry/helper logic) and pass it via `session.store`. It overrides `storageType`.

```ts
import { BaseSessionRepository, NestAuthModule } from '@ackplus/nest-auth';

class DynamoSessionStore extends BaseSessionRepository {
  constructor(private readonly db: DynamoClient) { super(); }
  async create(session) { /* … */ }
  async findById(id) { /* … */ }
  // …implement the rest of the SessionStore methods
}

NestAuthModule.forRoot({
  session: { store: new DynamoSessionStore(myDynamoClient) },
});
```

`store` accepts a ready instance **or** a factory for async setup:

```ts
session: { store: async () => MyKvSessionStore.connect(env.KV_URL) }
```

The `SessionStore` interface is small (`create`, `findById`, `findByUserId`, `findActiveByUserId`, `update`, `delete`, `deleteByUserId`, `deleteExpired`, `countActiveByUserId`, `updateLastActive`). You control your store's own dependencies — nest-auth just calls these methods for every session operation.
